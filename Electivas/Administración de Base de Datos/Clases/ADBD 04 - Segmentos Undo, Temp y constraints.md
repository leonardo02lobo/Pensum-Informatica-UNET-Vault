# ADBD 04 - Segmentos Undo, Temp y constraints

Materia: [[Administración de Base de Datos]]
Anterior: [[ADBD 03 - Volumetría y crecimiento]]
Siguiente: [[ADBD 05 - Perfiles y usuarios]]

## Contexto y objetivo
La Unidad III del material de clase ("Componente base de datos y estructuras de almacenamiento lógicas", semanas 9 y 10) cubre los **segmentos especiales** (Undo y Temp) y la **integridad de datos** mediante restricciones (constraints). Objetivo: configurar UNDO y TEMP, y crear y validar constraints con sus estados.

## Teoría

### Segmentos Undo (deshacer)
Guardan la imagen anterior de los datos modificados por transacciones. Funciones: *rollback*, **consistencia de lectura** (una consulta ve el dato tal como estaba al iniciarse), recuperación de transacciones fallidas y *flashback*. Dos modos: manual (rollback segments) y **automático** (`UNDO_MANAGEMENT=AUTO`), con un tablespace UNDO y los parámetros:
- `UNDO_RETENTION` (segundos que se intenta conservar undo confirmado).
- `RETENTION GUARANTEE` en el tablespace: garantiza esa retención aunque falle una transacción por falta de espacio.
Un error típico por retención corta: `ORA-01555 snapshot too old`.

### Segmentos temporales
Los usa Oracle para ordenamientos, `GROUP BY`, hash joins e índices en construcción que no caben en la PGA. Residen en un **tablespace TEMP** formado por *tempfiles*. Pueden ser del tablespace SYSTEM o de otros (no-SYSTEM). Se recomienda `UNIFORM` en TEMP y un **grupo de tablespaces temporales** para repartir carga.

### Integridad: constraints
Tipos: `NOT NULL`, `UNIQUE`, `PRIMARY KEY`, `FOREIGN KEY`, `CHECK`. Estados combinables:
| Estado | Efecto |
|---|---|
| `ENABLE VALIDATE` | Verifica filas nuevas y existentes |
| `ENABLE NOVALIDATE` | Solo filas nuevas |
| `DISABLE` | No verifica |
| `DEFERRABLE INITIALLY DEFERRED` | Se verifica al `COMMIT` |
Los índices que respaldan `PRIMARY KEY` y `UNIQUE` pueden ubicarse en un tablespace dedicado (`USING INDEX TABLESPACE`), requisito del informe del curso.

Constraints violadas pueden registrarse con la tabla `EXCEPTIONS` (script `utlexpt1.sql`) mediante `EXCEPTIONS INTO`.

## Ejemplo resuelto
El proyecto (Informe 2) creó `TS_COMEDOR_UNDO` con retención garantizada y `TS_COMEDOR_TEMP` uniforme, además de un tablespace para constraints de 128 MB con 48 índices de PK/UNIQUE y 169 constraints en total.

```sql
-- 1. Diagnóstico
SELECT tablespace_name, contents, retention FROM dba_tablespaces
 WHERE contents IN ('UNDO','TEMPORARY');
SHOW PARAMETER undo

-- 2. Undo propio con retención garantizada
CREATE UNDO TABLESPACE ts_comedor_undo
    DATAFILE '/opt/oracle/oradata/XE/XEPDB1/undo_comedor01.dbf' SIZE 256M
    AUTOEXTEND ON NEXT 16M MAXSIZE 1G;
ALTER TABLESPACE ts_comedor_undo RETENTION GUARANTEE;
ALTER SYSTEM SET UNDO_TABLESPACE = ts_comedor_undo SCOPE = BOTH;
ALTER SYSTEM SET UNDO_RETENTION = 3600 SCOPE = BOTH;

-- 3. Temp uniforme
CREATE TEMPORARY TABLESPACE ts_comedor_temp
    TEMPFILE '/opt/oracle/oradata/XE/XEPDB1/temp_comedor01.dbf' SIZE 256M
    AUTOEXTEND ON NEXT 32M MAXSIZE 1G
    EXTENT MANAGEMENT LOCAL UNIFORM SIZE 2M;
ALTER DATABASE DEFAULT TEMPORARY TABLESPACE ts_comedor_temp;

-- 4. Constraints con su índice en tablespace propio
CREATE TABLE beneficiaries (
    id          NUMBER(10) GENERATED BY DEFAULT AS IDENTITY,
    document_id VARCHAR2(20 CHAR) NOT NULL,
    activo      NUMBER(1) DEFAULT 1,
    CONSTRAINT pk_benef PRIMARY KEY (id)
        USING INDEX TABLESPACE ts_comedor_constraints,
    CONSTRAINT uq_benef_doc UNIQUE (document_id)
        USING INDEX TABLESPACE ts_comedor_constraints,
    CONSTRAINT ck_benef_activo CHECK (activo IN (0,1))
);

-- 5. Violación y comprobación
INSERT INTO beneficiaries (document_id, activo) VALUES ('V1', 5);  -- ORA-02290
SELECT constraint_name, constraint_type, status, validated, deferrable
  FROM user_constraints WHERE table_name = 'BENEFICIARIES';
```
Paso a paso: se diagnostica primero qué existe; se crea y se conmuta UNDO y TEMP; se crean constraints con el índice en su tablespace; se provoca `ORA-02290` (CHECK violado) y se comprueba el estado en el diccionario. Un `ORA-00001` indica violación de unicidad; `ORA-02291` (padre no existe) y `ORA-02292` (hay hijos) son de clave foránea.

Constraint con estado diferido y excepciones:
```sql
ALTER TABLE beneficiaries ADD CONSTRAINT ck_x CHECK (activo >= 0)
    ENABLE NOVALIDATE;
@?/rdbms/admin/utlexpt1.sql
ALTER TABLE beneficiaries ENABLE VALIDATE CONSTRAINT ck_x
    EXCEPTIONS INTO exceptions;
```

## Errores comunes
- Olvidar que `ORA-01555` se resuelve con retención y tamaño de undo, no solo reintentando.
- Un único TEMP pequeño que se llena en ordenamientos grandes (`ORA-01652`).
- Habilitar constraints con `VALIDATE` sobre datos sucios sin tabla `EXCEPTIONS`.
- Dejar índices de constraints en el tablespace de datos y nombrar constraints sin convención (el sistema asigna `SYS_C...`).

## Ejercicios propuestos
1. ¿Qué garantiza `RETENTION GUARANTEE`? *Respuesta: no se sobrescribe undo confirmado dentro del período de retención aunque eso haga fallar transacciones.*
2. ¿Cómo cargar datos legados con posibles violaciones y luego depurarlos? *Respuesta: `ENABLE NOVALIDATE`, luego `ENABLE VALIDATE ... EXCEPTIONS INTO`.*
3. ¿Qué consulta muestra constraints deshabilitadas? *Respuesta: `SELECT constraint_name FROM user_constraints WHERE status='DISABLED';`.*
