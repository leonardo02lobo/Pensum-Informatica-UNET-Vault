## Arquitectura de esquemas
El DDL empieza con `DROP SCHEMA ... CASCADE` y crea tres esquemas:
- `dwh`: modelo dimensional (capa de presentación).
- `stg`: staging, copia cruda del Excel sin transformar.
- `etl`: metadatos de control (marca de agua y bitácora `log_ejecucion`, `control_carga`).
Separar capas permite auditar el origen y reprocesar sin perder datos.

## Modelo en estrella
Un hecho y seis dimensiones:
```
dim_tiempo   dim_estudiante -- dim_carrera
      \         |
       hecho_atenciones -- dim_asesor -- dim_tipo_modalidad
                  |                          |
              dim_apoyo ---------------------+
```
- **Grano**: una atención brindada a un estudiante por un asesor, en una fecha, mediante un servicio de apoyo.
- **Medidas**: `duracion_minutos`, `satisfaccion` (1 a 5).
- **Clave primaria del hecho**: `id_atencion` (clave degenerada del origen).

## Tablas y decisiones
| Tabla | Tipo | Detalle |
|---|---|---|
| `dim_carrera` | SCD1 con borrado lógico | `vigente`, `nombre_carrera` único |
| `calendario_semestre` | parámetros | rangos de cada semestre; `CHECK (semestre <> 'Receso')` |
| `dim_tiempo` | calendario | `id_tiempo` IDENTITY, `fecha` UNIQUE, `semestre_academico` |
| `dim_tipo_modalidad` | de combinación | tipo × modalidad (8 filas; modalidad Presencial o Virtual) |
| `dim_apoyo` | servicio | FK a tipo/modalidad, único `(nombre, id_tipo_modalidad)` |
| `dim_asesor` | SCD2 por vigencia | `fecha_inicio_vigencia`, `fecha_fin_vigencia`, `vigente` |
| `dim_estudiante` | SCD2 real | clave de negocio `cedula`, `id_estudiante` IDENTITY |
| `hecho_atenciones` | hecho | 4 FKs + 2 medidas |

### Restricciones destacadas
- Coherencia de calendario: `ck_dim_tiempo_coh` obliga a que `dia`, `mes`, `anio` coincidan con `fecha` (`EXTRACT`).
- Vigencia SCD2: `(vigente AND fecha_fin IS NULL) OR (NOT vigente AND fecha_fin IS NOT NULL AND fecha_fin >= fecha_inicio)`: la fila vigente no tiene cierre y la histórica sí.
- `GENERATED BY DEFAULT AS IDENTITY`: la clave subrogada la asigna una secuencia; `BY DEFAULT` permite cargar ids explícitos en la carga inicial del histórico.
- Género `'M','F','N'`: `'N'` reservado para el **miembro desconocido** (`id_estudiante = -1`).
- Índice único parcial `(cedula) WHERE vigente`: una sola versión vigente por cédula.

Fragmento real:
```sql
CREATE TABLE dwh.dim_asesor (
    id_asesor INTEGER NOT NULL, nombre VARCHAR(50) NOT NULL, ...
    fecha_inicio_vigencia DATE NOT NULL, fecha_fin_vigencia DATE,
    vigente BOOLEAN NOT NULL DEFAULT TRUE,
    CONSTRAINT ck_dim_asesor_vigencia CHECK (
        (vigente AND fecha_fin_vigencia IS NULL)
     OR (NOT vigente AND fecha_fin_vigencia IS NOT NULL
                     AND fecha_fin_vigencia >= fecha_inicio_vigencia)));
```

## Decisiones de diseño (README)
1. **Claves subrogadas propiedad del DWH**; el origen entrega fecha y cédula, el ETL resuelve.
2. `id_tiempo` por secuencia en lugar de `YYYYMMDD` (decisión de costo: evita migrar los 5.520 hechos ya cargados).
3. El semestre es un **parámetro** (`calendario_semestre`), no una fórmula.
4. `Receso` cubre días fuera de semestre (518 días de calendario, 76 en receso); las consultas lo excluyen.
5. Cuatro tipos de apoyo: Académico, Psicológico, Socioeconómico, Vocacional.
6. Ruta del **apoyo** autoritativa para la modalidad; el control 5 verifica coherencia con el asesor.
7. Umbrales mínimos en rankings (10 atenciones en P4, 20 en P3b).

## Ejemplo resuelto: ¿por qué una dimensión de combinación?
Tipo (4 valores) y modalidad (2 valores) generan 8 combinaciones. Almacenarlas en una pequeña dimensión evita repetir cadenas en `dim_apoyo` y `dim_asesor` y permite filtrar por una única clave. Si la modalidad se guardara en ambas tablas por separado, podrían contradecirse: por eso existe el control de calidad 5.

## Errores comunes
- Definir el grano a mitad del diseño.
- Usar la cédula como clave primaria de `dim_estudiante` (impide versionar).
- Olvidar el índice parcial y permitir dos versiones vigentes.
- Cargar hechos antes de dimensiones (viola FK).

## Ejercicios propuestos
1. Añada una dimensión `dim_sede`. *Resp.: tabla con clave subrogada, FK `id_sede` en el hecho, actualizar ETL y controles.*
2. ¿Por qué `fecha_fin_vigencia` es NULL en la fila vigente? *Resp.: representa "sin fin"; el CHECK lo impone.*
3. Escriba el CHECK para satisfacción 1-5. *Resp.: `CHECK (satisfaccion BETWEEN 1 AND 5)`.*
